# store/fs — технические решения

## Атомарная запись (io.go::atomicWrite)

**Решение**: запись в temp-файл в той же директории, затем `os.Rename`.

**Почему**: `os.Rename` в пределах одной ФС атомарен на уровне ядра. Читатель никогда не увидит частично записанный файл. Если процесс падает между записью во temp и rename — temp остаётся как мусор (`.tmp-*`), исходный файл не повреждён.

**Почему temp в той же директории**: `os.Rename` между разными ФС/разделами не атомарен (превращается в copy+delete). Temp-файл должен быть на том же разделе что и target.

**Дескриптор закрывается явно до rename**: defer используется только для cleanup при ошибке, не для закрытия. Причина: на Windows открытый дескриптор блокирует rename; на Linux это допустимо, но явное закрытие — правильная практика.

## Сохранение created_at при upsert (upsert.go)

**Решение**: при upsert читается существующая запись, извлекается `created_at`, новая запись получает исходный `created_at` и текущий `updated_at`.

**Почему**: семантика upsert — "создай или обнови". Дата создания не должна меняться при обновлении. Стор управляет timestamps полностью — клиент не может их подделать.

**Если существующий файл нечитаем**: возвращается `ErrReadExisting`. Upsert не продолжается — данные могут быть повреждены, перезаписывать небезопасно.

## Path traversal protection (validate.go::recordPath)

**Решение**: после `filepath.Join(basedir, id+".json")` проверяется что результат начинается с `filepath.Clean(basedir)+separator`.

**Почему**: ID приходит от клиента через JSONL-протокол. ID вроде `../../../etc/passwd` без проверки дали бы доступ за пределы basedir. Проверка выполняется до любого IO.

**Что считается невалидным**: любой ID, путь которого после Clean выходит за пределы basedir. Возвращается `ErrMissingID`.

## Entity как прямой receiver, Relation/Job через обёртки

**Решение**: `Store` напрямую реализует `EntityStore` (методы на `*Store`). `RelationStore` и `JobStore` — через обёртки `relationStore` и `jobStore`.

**Почему**: Entity-методы реализовывались первыми. При добавлении Relation и Job было невозможно добавить методы с теми же именами (`Upsert`, `Get`, `Delete`, `List`) на `*Store` — конфликт имён. Обёртки решают это без переименования методов.

**Consequence**: `s.Entities()` возвращает сам `s`, `s.Relations()` и `s.Jobs()` возвращают обёртки. Это нормально — все три удовлетворяют соответствующим интерфейсам.

**При добавлении нового типа хранилища**: Entity-методы потребуется перенести в отдельную обёртку (аналогично Relation/Job), что изменит поведение `s.Entities()` — он будет возвращать обёртку, а не сам `s`.
