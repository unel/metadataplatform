# Review 2: scripts-design.md

Ревьюер: Гримм
Дата: 2026-05-06

## CRITICAL

**1. cascade-stale: алгоритм граф-обхода сломан для fix-шагов.**

`next-step` прописывается при инициализации скелета и отражает линейный happy path. Если `01-spec/02-review` имеет `next-step: 02-acceptance/01-write`, а в пайплайне существует `01-spec/03-fix` — он будет пропущен при каскаде. Нужно уточнить: `next-step` ссылается на **все** downstream-шаги включая fix-шаги, или только на happy-path? Если только happy-path — алгоритм каскада будет пропускать узлы.

**2. begin-step: не проверяет текущий статус шага.**

Если шаг уже `in-progress` — скрипт тихо добавит вторую запись `in-progress` в лог. Получим два "текущих рана" без ошибки. Нужна проверка: если последний статус уже `in-progress` → stderr + `exit 1`.

**3. end-step: cascade-stale вызывается без --dry-run при dry-run end-step.**

Документ: "Вызывает `cascade-stale` (автоматически, без `--dry-run`)". Если пользователь вызвал `end-step --dry-run` — запустится реальный cascade-stale и произведёт реальные изменения. Ломает семантику `--dry-run`. Нужно либо передавать `--dry-run` в cascade-stale, либо явно задокументировать.

**4. --amend: нет защиты от инконсистентного состояния.**

`--amend` перезаписывает последнюю запись, но cascade-stale не повторяется. Если статус меняется через amend (например с `done` на `failed`) — downstream уже stale-нулся по-старому. Минимум: задокументировать что `--amend` не перезапускает cascade-stale и пользователь обязан вызвать его вручную.

## MEDIUM

**5. parse_frontmatter: двоеточие в значении обрезает значение.**

```python
k, _, v = line.partition(':')
```
Поле вида `message: Фикс: уточнить поведение` обрежет значение до `Фикс`. Правильно: `line.split(':', 1)` и брать второй элемент целиком.

**6. inconsistent-детект: условие неполное.**

Не учтён кейс: `brief-NNN.md` **отсутствует**, но статус `in-progress`. Это тоже inconsistent — бриф пропал (удаление, git checkout). `feature-status.sh` покажет `in-progress` без пометки.

**7. filesystem order: неявная зависимость от конвенции именования.**

Дизайн неявно зависит от числовых префиксов в именах директорий, но не документирует это требование явно.

**8. log-note/complaint: резолюция через feature-status — скрытая зависимость.**

Subprocess-вызов без описания как парсить вывод. `--json` был бы надёжнее для машинного чтения из скрипта.

**9. end-step: обновление run в frontmatter нарушает append-only принцип.**

Инкремент `run` в frontmatter — это перезапись файла, не append. Формально противоречит принципу. Важнее: нет атомарности (stdlib даёт `fcntl.flock` для POSIX — приемлемо, но не упомянуто).

## MINOR

**10. --unique семантика неточная.**

`--unique` определён как shortcut для `--max-matches 1`, но семантически звучит как "упасть если найдено > 1". Либо переименовать в `--first`, либо добавить поведение "если найдено > 1 → stderr + exit 1".

**11. Нет описания exit codes.**

Какой exit code при `--dry-run`? При `unknown status` (только предупреждение)? При `warning: active step not found`?

**12. Расширение .sh у Python-скриптов.**

Вводит в заблуждение. Либо `.py`, либо без расширения.

---

## Что упущено

**Конкурентный доступ**: скрипты не документируют что делать при конкурентной записи в status-log.md.

**--from/--to несвязанные шаги в cascade-stale**: алгоритм обхода по `next-step` может никогда не дойти до `--to` если он не в цепочке. Поведение не описано.

**Инициализация frontmatter**: `begin-step` п.5 говорит "добавляет frontmatter если не было". Добавление в начало файла — единственный случай когда status-log.md модифицируется не append-only. Это не описано явно.
