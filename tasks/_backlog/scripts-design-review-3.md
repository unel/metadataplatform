# Review 3: scripts-design.md

Ревьюер: Гримм
Дата: 2026-05-06

---

## CRITICAL

**1. begin-step: recovery-логика проверяет неправильный ран.**

`max(run=N)` по **всем** записям вернёт N+1 если ран уже открыт (в строке `in-progress run=N+1`). Значит скрипт будет искать `brief-{N+2:03d}.md` вместо `brief-{N+1:03d}.md` и упадёт с exit 1 вместо recovery. Два определения «текущего рана» конфликтуют внутри одного алгоритма.

**2. cascade-stale: `pending` пропускается молча.**

Обход идёт по всей цепочке, `pending`-шаги пропускаются при записи — downstream `done`-шаги за `pending` получат `stale`. Это верно. Но `--dry-run` не показывает пропущенные шаги. Пользователь не увидит что шаг посередине был пропущен. Dry-run должен явно выводить пропущенные шаги с причиной.

**3. end-step: нет проверки что begin-step действительно был вызван для этого рана.**

Можно вызвать `end-step` без предшествующего `begin-step` — достаточно положить `brief-NNN.md` и `report-NNN.md`. Запись `in-progress run=N` в статус-логе при этом отсутствует, но `end-step` пишет `done run=N`. Статус-лог не будет содержать `in-progress`-записи для этого рана.

## MEDIUM

**4. --amend: парсинг «последней записи» не специфицирован. Многострочный комментарий?**

Если комментарий может быть многострочным — парсинг нетривиален. Если нет — ограничение не задокументировано. Агент напишет многострочный `--message` и получит битый файл или обрезанный amend.

**5. inconsistent `detail` — формат не описан для каждого кейса.**

Таблица даёт причины словами, но что именно попадает в JSON `"detail"` — не специфицировано. Агент читает JSON и должен понимать тип проблемы.

**6. log-note: контракт subprocess с feature-status.py не зафиксирован.**

`feature-status.py --json` без `--all` возвращает объект (одна фича). Это нигде не записано как контракт. Если поведение изменится — `log-note.py` сломается молча.

**7. Формат записи в notes/complaints не специфицирован.**

Три строки слитно или с пустой строкой между ними? Агенты в `06-retro/01-recall` читают эти файлы — если формат не определён, парсинг будет гадать.

---

## MINOR

**8. begin-step recovery нарушает append-only.**

Recovery «обновляет datetime в последней строке» — это перезапись, не append. Truncate+rewrite или seek — нетривиально и error-prone для больших файлов. Либо recovery добавляет новую `in-progress`-запись (допуская дублирование), либо append-only нарушается явно и это описывается.

**9. `stale` не несёт `run=N` — взаимодействие со счётчиком не описано.**

После `done run=3` → `stale` → max run по файлу = 3. При следующем begin-step ожидается `brief-004.md`. Это корректно, но нигде не описано. Агент видит `stale`-шаг и не знает какой номер brief создавать.

**10. cascade-stale + `pending` посередине `--from`/`--to` — поведение не специфицировано.**

A (`done`) → B (`pending`) → C (`done`) → D (`done`). `--from A --to D`. B пропускается. C и D получают `stale`. Ожидаемо? Или `pending` должен останавливать каскад?

## Что упущено

**Кто создаёт `status-log.md` с frontmatter.** `begin-step` предполагает что файл уже есть. Если scaffold-скрипт отдельный — его нет в дизайне. Если это ответственность агента — не задокументировано.

**06-retro + cascade-stale + feature-status взаимодействие.** `feature-status.py` подберёт шаги `06-retro` через `rglob`. Активный шаг может определиться как `06-retro/01-recall`. LLM-агент вызовет `end-step` и ожидает cascade-stale — но у `06-retro` нет `next-success-step`, каскад не произойдёт. Поведение нигде не предупреждено.
