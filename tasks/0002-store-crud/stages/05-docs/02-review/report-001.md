## Замечания

### `store/router/README.md` — таблица кодов ошибок, READ_ERROR

**Категория:** warning
**Проблема:** `READ_ERROR` описан как "Ошибка чтения записи из хранилища". Но этот код покрывает как `store.ErrReadRecord` (данные просто не прочитаны), так и `store.ErrReadExisting` (upsert отменён — существующая запись нечитаема, новые данные не записаны). Клиент, получив `READ_ERROR` на upsert, не может определить: его данные записались или нет. Семантика принципиально разная.
**Рекомендация:** Добавить примечание к `READ_ERROR`: "При upsert означает что существующая запись нечитаема — операция отменена, новые данные не записаны."

### `store/README.md` — "default {}" в описании полей

**Категория:** warning
**Проблема:** В описании полей типов Entity, Relation, Job указано "default {}". Это ложное ожидание: поля `json.RawMessage` без `omitempty` при nil-значении сериализуются как `null`, а не `{}`. Разработчик создаст `store.Entity{}` с нулевым Meta и получит `"meta": null` в хранилище.
**Рекомендация:** Убрать "default {}" или добавить явное примечание: "При nil сериализуется как null. Для пустого объекта передавай `json.RawMessage([]byte(`{}`))` явно."

### `store/README.md` — пример Upsert не компилируется

**Категория:** Nit:
**Проблема:** `Meta: json.RawMessage(\`{"path": ...}\`)` — прямое присваивание строкового литерала к `json.RawMessage` (`[]byte`) не компилируется в Go.
**Рекомендация:** Исправить на `Meta: json.RawMessage([]byte(\`{"path": "/data/file.mp4", "size": 104857600}\`))`.

### `store/router/README.md` — MISSING_ID при отсутствии поля id

**Категория:** Nit:
**Проблема:** Таблица кодов ошибок не объясняет что при отсутствующем `id` в get/delete клиент получает `MISSING_ID`, а не `INVALID_REQUEST`. Это контринтуитивно — валидация id происходит в сторе, не в роутере.
**Рекомендация:** В описании `MISSING_ID` добавить: "Включает случай когда поле `id` не передано в запросе get/delete."

### `store/router/README.md` — примеры ответов без реальных полей

**Категория:** Nit:
**Проблема:** Примеры ответов для get/list показывают `{"ok": true, "data": {...}}` без реальных полей. Читатель не видит что data содержит `id`, `type`, `created_at`, `updated_at`, `meta` и т.д.
**Рекомендация:** Добавить один пример полного ответа get entity с реальными полями.

### `store/fs/README.md` — логирование через роутер

**Категория:** Nit:
**Проблема:** Раздел "Логирование": "Debug — успешные операции (через роутер)" вводит в заблуждение. FS-стор сам по себе логирует только инициализацию. Debug/Error при операциях — в `store/router`, не в `store/fs`.
**Рекомендация:** Переформулировать: "store/fs логирует только инициализацию (Info). Логирование операций (Debug/Error) — в store/router."

### `store/fs/TECH.md` — эволюционное последствие Entity receiver

**Рекомендация:** Добавить: "При добавлении нового типа хранилища Entity-методы потребуется перенести в отдельную обёртку, что изменит поведение `s.Entities()`."
