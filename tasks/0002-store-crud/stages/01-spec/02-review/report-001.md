## Замечания

### CR-1 [warning]

> "Если запись не существует — вернуть ошибку. Delete **не идемпотентный**." (§3.3)

Delete намеренно не идемпотентен — но обоснование нигде не зафиксировано. Протокол JSONL используется spawner'ом и platform CLI. При retry после сбоя повторный delete вернёт `NOT_FOUND` — spawner обязан обрабатывать это как ошибку, хотя желаемый эффект достигнут. В разделе "Решения принятые в процессе" этого нет. Нужно явно зафиксировать: намерение + обоснование.

### CR-2 [warning]

> "Вернуть все записи данного типа." (§3.4 List)

Порядок элементов в ответе `List` не определён. FS: `os.ReadDir` возвращает файлы отсортированными по имени (UUID v7 — монотонно возрастающий, порядок детерминирован). Но спека не фиксирует этот контракт. Тест-writer напишет `assert.Equal(t, []Entity{a, b}, result)` — тест станет флаки при смене реализации. Нужно либо: "порядок не гарантирован, тесты не проверяют порядок", либо: "List возвращает в порядке возрастания `id`".

### CR-3 [warning]

> Схема БД: `relations` содержит колонку `search_tsv tsvector` (PROJECT.md)
> Go-структура `Relation` (§2.2): поля `search_tsv` нет.

Расхождение не объяснено. Варианты: (a) поле исключено намеренно для FS-реализации — нужно написать явно; (b) нужно добавить в struct с тегом `json:"-"` и комментарием для PG-реализации. Тест-writer и code-writer упрутся в этот вопрос.

Дополнительно: FS-реализация не проверяет существование `from_id` / `to_id` при upsert relation. В PG это FK-констрейнт. Spec не описывает поведение FS при upsert relation с несуществующим entity. Это `WRITE_ERROR`? Молча игнорируется?

### CR-4 [note]

> "Парсинг: `json.NewDecoder` на `net.Conn`, цикл `Decode()`." (§5.1)

Поведение при `io.EOF` или `io.ErrUnexpectedEOF` от `Decode()` не описано. Это штатная ситуация: клиент закрыл соединение. Роутер должен выйти из цикла без логирования ошибки. Без явного описания code-writer залогирует `io.EOF` как ошибку — логи забьются шумом от каждого нормального закрытия соединения.

### CR-5 [note]

> "Второй decode `data` → конкретная структура (только для upsert)." (§5.2)

Поведение при `{"op":"upsert","type":"entity","data":null}` не описано. Технически: `json.Unmarshal(null, &Entity{})` даёт нулевой Entity с пустым `id` → `MISSING_ID`. Работает случайно, не по дизайну. Нужно явно: "если `data` отсутствует или null — `INVALID_REQUEST`", или подтвердить что `MISSING_ID` — ожидаемый путь.

### CR-6 [note]

> "НФТ-О-1. Логирование ошибок." (§НФТ)

Логирование успешных операций не определено. FS — debug-only. `INFO upsert entity id=<uuid>` было бы полезно. Это осознанное "не логируем успех" или пробел? Если осознанное — написать явно.

### CR-7 [note]

> "При будущей параллельной реализации — при ошибке в одной горутине отменить все остальные." (§3.4, §НФТ-Н-4)

Спека упоминает отмену горутин дважды, но не описывает контракт передачи `context.Context` в горутины List. Без ctx propagation прямо сейчас — отмена в будущем невозможна без переработки сигнатуры. Нужно явно зафиксировать что `ctx` пробрасывается в операции List уже сейчас.

### CR-8 [note]

> "При любой ошибке на шагах 2–5 — `os.Remove(tmpPath)`." (§4.3)

Cleanup не уточнён как `defer` с проверкой ошибки. При panic temp-файл не будет убран через if-err-branch. Для debug-only — minor, но паттерн станет источником утечек в будущих реализациях. Рекомендация: "cleanup через `defer` с захватом переменной ошибки".
