## Замечания

### CR-14 [critical]

> §4.3, шаг 2: "Сразу после создания: `defer func() { if err != nil { os.Remove(tmpPath) } }()` — cleanup при любой ошибке или panic."

Паттерн требует именованного возврата ошибки (`func (...) (err error)`). Без named return переменная `err` внутри defer-замыкания — это замкнутая копия на момент объявления, не переменная возврата функции. При выходе из функции через `return someErr` переменная `err` в defer по-прежнему `nil`, cleanup не выполняется, temp-файл утекает.

Спека предписывает конкретный синтаксис паттерна, но не предписывает named return error в сигнатуре функции. Без этого указания code-writer напишет код который не защищает от утечки — ровно то, от чего §НФТ-Н-3 должна защищать.

Нужно добавить явно: функция atomic write должна использовать named return `(err error)`. Пример:

```go
func (s *Store) upsert(ctx context.Context, ...) (err error) {
    tmp, _ := os.CreateTemp(...)
    defer func() {
        if err != nil {
            os.Remove(tmp.Name())
        }
    }()
    ...
}
```

Без этого §НФТ-Н-3 и §4.3 шаг 2 не выполняют своей цели.

### CR-15 [warning]

> §4.1: "Субдиректории создаются при инициализации." §4.3: имя файла формируется как `{basedir}/entities/{id}.json`. §6: UUID v7, генерация клиентская.

Спека не требует санитизации `id` перед использованием в качестве имени файла. FS-реализация будет конструировать путь на основе `id` из входящего запроса — клиентской строки. Go `filepath.Join` нормализует `..`, но не все способы конкатенации пути одинаково безопасны. Если code-writer использует `fmt.Sprintf("%s/%s.json", dir, id)` вместо `filepath.Join` — `id = "../../../etc/cron.d/evil"` даёт запись за пределами `basedir`.

Спека продекларирована как debug-only (§НФТ-О-Р-3), но path traversal не становится менее опасным от этого статуса.

Нужно добавить в §4.1 или §4.3: "Путь формируется через `filepath.Join(dir, id+".json")`. Прямая конкатенация строк запрещена."

### CR-16 [warning]

> §НФТ-О-1: "Ошибки: `ERROR op=<op> type=<type> id=<id> error="<text>"`" и "Успешные операции: `DEBUG op=<op> type=<type> id=<id>`"

Спека не указывает где именно происходит логирование — в роутере или в FS-реализации. FS знает тип операции (Upsert/Get/Delete/List), но не знает `op` из envelope. Роутер знает `op` и `type` из envelope, но не видит деталей IO.

Два code-writer'а (FS и роутер) сделают разные выводы. Нужно явно определить ответственный компонент.
