## Замечания

### CR-17 [warning]

> §4.3, алгоритм atomic write, шаги 5–6: `f.Sync()`, `f.Close()`.

Спека предписывает cleanup temp-файла через defer, но не предписывает `defer f.Close()`. При любой ошибке до шага 6 функция возвращается с открытым файловым дескриптором — fd утекает. Нужно добавить в алгоритм §4.3 явный `defer f.Close()` после создания temp-файла.

### CR-18 [warning]

> §3.1 Upsert, Failure modes: только MISSING_ID и WRITE_ERROR.
> §4.3, шаг 3: "При обновлении: created_at читается из существующей записи."

Чтение существующей записи при upsert может завершиться ошибкой (файл повреждён). Спека не определяет errorCode для этого случая. Code-writer вернёт WRITE_ERROR (семантически неверно), придумает новый errorCode или проигнорирует ошибку.

Нужно добавить в §3.1 failure modes: ошибка чтения существующей записи при upsert → errorCode и сообщение.

### CR-19 [warning]

> §4.3: сигнатура `func (s *Store) upsert(ctx context.Context, path string, obj any) (err error)`.
> §4.3, шаг 3: "Выставить created_at/updated_at по правилам §3.1."

Конфликт: `obj any` + установка временных меток внутри функции требует type switch на все три типа или рефлексию. Если метки выставл��ются снаружи — шаг 3 в алгоритме лишний. Нужно явно определить где выставляются метки.

### CR-20 [warning]

> §5.1: роутер продолжает обработку после ошибки. §НФТ-Б-1: соединение не разрывается.

`json.Decoder` после decode-ошибки наход��тся в неопределённом состоянии — следующий `Decode()` может не восстановиться. Два требования спеки (json.Decoder + recovery) физически несовместимы без дополнительного указания. Нужно явно опреде��ить поведение после decode-ошибки.
