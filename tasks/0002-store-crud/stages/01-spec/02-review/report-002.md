## Замечания

### CR-9 [warning]

> §4.1: "Субдиректории создаются при инициализации если не существуют." §НФТ-О-2: "INFO store/fs initialized basedir=<path>"

Failure mode инициализации FS не описан. Если `os.MkdirAll` возвращает ошибку при старте — поведение не определено нигде: нет в failure mode таблицах операций, нет в §7, нет лог-строки для ошибки инициализации. Startup failure означает что роутер стартует без рабочего хранилища и все последующие upsert падают с `WRITE_ERROR` без понятной причины. Нужно явно: если инициализация провалилась — вернуть ошибку из конструктора и залогировать `ERROR store/fs init failed basedir=<path> error=<...>`.

### CR-10 [warning]

> §1.1: "Интерфейсы определяются на стороне потребителя (пакет `store`)" + §5: JSONL-роутер маппит входящие JSONL-команды на вызовы трёх интерфейсов.

Роутер (§5) использует `EntityStore`, `RelationStore`, `JobStore` — но спека не описывает структуру пакетов и механизм инъекции. Роутер в пакете `store` или отдельном? Сигнатура конструктора? Без этого acceptance-writer не напишет сценарии тестирования роутера с mock-хранилищем. Тест-writer без явной инъекции завяжется на реальную FS. Нужно: структура пакетов (хотя бы: `store/`, `store/fs/`, роутер где?) и сигнатура конструктора роутера.

### CR-11 [note]

> §НФТ-О-1: "Успешные операции: `DEBUG op=<op> type=<type> id=<id>`"

Формат лог-строки для операции `list` не определён. `list` не принимает `id` — поле `id` в лог-строке не применимо. Code-writer залогирует либо `id=""`, либо пропустит поле, либо добавит `count=N`. Нужно: "для list — `DEBUG op=list type=<type> count=<N>`", или явно: "поле `id` опускается если не применимо".

### CR-12 [note]

> §5.2: Envelope: `{"op":"...","type":"...","id":"...","data":json.RawMessage}` + §3.1: "Входные данные: объект типа с заполненным `id`"

Поведение при конфликте `id` в envelope и `id` внутри `data.id` для upsert не описано. Для `get`/`delete` `id` берётся из envelope. Для `upsert` — из `data`. Но спека не говорит этого явно. Запрос `{"op":"upsert","type":"entity","id":"aaa","data":{"id":"bbb",...}}` — какой `id` использует стор? Нужна одна строка: "для upsert поле `id` в envelope игнорируется — `id` берётся из `data`".

### CR-13 [note]

> §3.1 п.5: "Значения `created_at` и `updated_at` из входящего запроса игнорируются." + §4.3: алгоритм atomic write.

Алгоритм §4.3 описывает только IO-операции: CreateTemp → encode → Sync → Close → Rename. Логика выставления `created_at`/`updated_at` в алгоритм не включена — она есть в §3.1 но туда не дублируется. Code-writer читающий §4.3 изолированно пропустит выставление временны́х меток. Нужно: добавить явный шаг "выставить created_at/updated_at по правилам §3.1 перед encode" или ссылку на §3.1 в §4.3.
