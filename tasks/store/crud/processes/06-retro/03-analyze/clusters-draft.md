# Кластеры проблем — store/crud retro analyze

25 проблем → 12 кластеров → 4 категории.

---

## ТРЕБОВАНИЯ

### 1. API-контракт до test-write
**Источник:** Азирафаль, Кроули, Гримм (косвенно)
**Что произошло:** Два тест-агента угадывали сигнатуры конструкторов и интерфейсов независимо. Азирафаль предположил `captureLogger` + метод `LogOp`; Кроули — `*slog.Logger` с router_helpers. Оба внутренне консистентны, между собой — нет. Кроме того, оба предположили что `*fs.Store` реализует все три интерфейса напрямую — в Go это невозможно из-за конфликта имён методов. Обнаружила Ада в 04-code при ошибке компиляции. Итог: 4+ лишних раунда review/fix.
**Root cause:** Acceptance не содержит раздела "API contracts" (сигнатуры конструкторов, имена интерфейсов). Action item из RETRO connection ("пример лог-строки, сигнатура конструктора") не был имплементирован — некуда было положить.

### 2. Спека Go-specific без разделения контракта и реализации
**Источник:** Танк, Ада, Кроули
**Что произошло:** Спека описывает `filepath.Join`, `named return`, конкретные Go-сигнатуры — смешивает "что делает" с "как именно реализовать на Go". Это провоцирует half-solutions: CR-15 добавил `filepath.Join` без проверки traversal — потому что спека предписала паттерн, но не описала полный инвариант. Тот же баг вылез как CRITICAL-1 в code-review.
**Root cause:** В шаблоне spec нет явных разделов "Контракт (языко-нейтральный)" и "Реализация на Go". Без структуры Go-специфика просачивается в требования автоматически.

### 3. Инварианты не документируются
**Источник:** Ада, Гримм
**Что произошло:** Инвариант "id строится в путь файла → id не может содержать `../`" был очевиден в момент написания `recordPath`, но не записан. CRITICAL-1 поймал ревьювер, не автор. Это рецидив из store/connection (CR-7 → deadlock: косметика меняла семантику, инвариант не был задокументирован).
**Root cause:** В AC нет обязательного пункта "инварианты валидации" для операций где пользовательские данные попадают в путь/команду/формат. Стандарт `// inv:` из RETRO connection не был добавлен в шаблоны.

## ПРОЦЕССНЫЕ

### 4. Action items retro не конвертируются в задачи
**Источник:** Танк, Гримм, Кроули
**Что произошло:** Из 8 пунктов "берём в работу" из RETRO store/connection — 0 выполнено к старту store/crud. Три из них (API-контракт, лог-формат в spec, grep после фикса) если бы были выполнены — сэкономили бы 2-3 раунда review в этой фиче.
**Root cause:** Ретро создаёт список без owner, дедлайна и места хранения. Нет шага "создать задачи в backlog". Без этого ретро — терапия без последствий.

### 5. Notes/complaints не пишутся по ходу работы
**Источник:** Все участники, пользователь (notes-user.md)
**Что произошло:** Ни один агент не оставил notes/complaints в ходе фичи. Все записали только на этапе recall — детали первых прогонов размыты. У Кроули и Азирафаль файлы лежали в неправильных местах.
**Root cause:** Формат донесён только в 06-retro/01-recall, не встроен в скиллы шагов. Notes/complaints — не обязательный выходной артефакт шага, а опциональная добавка.

### 6. Порядок шагов нарушен: spec pending → code done
**Источник:** Танк
**Что произошло:** spec-ft, spec-nft, spec-review остались в pending. test-write, code, code-review помечены done. Код написан и отревьюен без формального контракта.
**Root cause:** В pipeline нет gate-проверки: оркестратор не блокирует переход когда вышестоящий шаг в pending. (⚠️ Открытый вопрос для пользователя: это была ошибка или сознательный пропуск?)

### 7. Нет fix-report / дыры в истории итераций
**Источник:** Танк, Ада
**Что произошло:** report-001 для первого 04-code/01-write не создан. Нет spec-fix-report ни в connection, ни в crud. История итераций восстанавливается только по status-log — контекст решений теряется.
**Root cause:** Тот же что в кластере 4: action item из RETRO connection ("fix-report обязателен") не имплементирован.

### 8. Граница 03-tests / 04-code размылась
**Источник:** Кроули, Азирафаль
**Что произошло:** Ада фиксила тесты в 04-code вместо возврата на 03-tests. Тесты не компилировались из-за архитектурных предположений (кластер 1); вместо clarification → 03-tests/03-fix Ада адаптировала тесты на месте. Граница ответственности нарушена.
**Root cause:** Нет жёсткого правила в workflow: если в 04-code обнаружено несоответствие тестов и реализации → clarification к 03-tests, не самостоятельный фикс.

### 9. Каскадный сброс статусов не валидируется
**Источник:** Гримм
**Что произошло:** test-review report-003 помечен done, но прошли ещё run-4 и run-5. Код менялся после закрытия test-review — статус не откатился в stale.
**Root cause:** Оркестратор вручную управляет каскадом. Нет автоматической или явной проверки перед переходом к следующему шагу.

### 10. Ретро запущено при незакрытых шагах
**Источник:** Гримм
**Что произошло:** 05-docs/02-review вернул failed (7 замечаний), fix запустился, сессия прервалась. Ретро стартовало до завершения docs-pipeline — нигде не задокументировано как сознательное решение.
**Root cause:** Нет pre-check перед стартом ретро: все шаги pipeline должны быть done или явно помечены как skipped.

## ИНСТРУМЕНТАЛЬНЫЕ

### 11. Compile-fail и test-fail неразличимы в стейт-логе
**Источник:** Кроули
**Что произошло:** "setup failed" одинаково логируется для "пакет ещё не написан (Red phase)" и "тест не компилируется из-за несовместимости типов (реальная ошибка)". Требует ручного разбора.
**Решение:** Разделить на два шага: `go vet + go build` (compile gate) и `go test` (test run). Compile-fail и test-fail — разные категории с разными последствиями.

### 12. Ревьюер без shell / без явного списка файлов
**Источник:** Гримм
**Что произошло:** Поиск report-NNN.md в untracked директориях — угадывание имён. Несколько попыток потрачено на несуществующие файлы.
**Решение (частичное):** Оркестратор передаёт явный список файлов для проверки в промпте. Доступ к shell для `ls`/`find` — архитектурный вопрос.

### 13. Чтение/запись status-логов и notes делается вручную — нужны мини-скрипты
**Источник:** пользователь ([tooling] в notes-user.md)
**Что произошло:** Статус фичи выясняется вручную: нужно открывать каждый status-log.md, читать последнюю запись, агрегировать картину. Дозапись жалоб и notes — аналогично руками или через агента. Это медленно, ошибкоёмко и приводит к тому что агенты пишут status-log неправильно (корневой status.md появился снова вместо status-log.md процессов).
**Связь:** Напрямую связан с кластером 5 (notes не пишутся) — если бы запись была через `log-note store/crud гримм "[friction] ..."`, барьер был бы ниже.
**Решение:** Серия мини-скриптов:
- `status <feature>` — агрегирует последние записи всех status-log.md, показывает pipeline одной командой
- `log-note <feature> <агент> "<тег> текст"` — дозапись в notes-<агент>.md без открытия файла
- `log-complaint <feature> <агент> "текст"` — аналогично для complaints
